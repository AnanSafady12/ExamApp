PROJECT GOAL
============
ExamApp is an online examination system built with React.
Teachers create and manage exams, students take exams and receive instant grading.
The project uses a mock API layer to simulate a backend server, making it ready for future migration to a real Node.js backend.


USERS
=====
1. Teacher
   - Creates, edits, and deletes exams
   - Views student scores per exam
   - Controls exam status (draft, published, closed)

2. Student
   - Browses available exams
   - Takes multiple-choice exams
   - Receives instant score and answer review after submission


PAGES & ROUTING
===============
The application utilizes React Router (HashRouter) to manage client-side routing, navigation menus, and protected role-based workspaces. Using HashRouter ensures robust support on static hostings like GitHub Pages by preventing deep reload 404 errors.

1. Home / Root Route (/)
   - Renders the HomeRedirect controller.
   - Evaluates the user's active session and instantly redirects them to the appropriate workspace:
     * Unauthenticated -> /login
     * TEACHER -> /teacher
     * STUDENT -> /student

2. Login Page (/login)
   - Username and password fields.
   - Redirects to root (/) if the user is already authenticated.
   - Displays demo accounts for quick testing.
   - Contains navigation Links to /register.

3. Register Page (/register)
   - Inputs: Full name, username, password, role selector (Student/Teacher).
   - Validates fields and checks for duplicate usernames.
   - Redirects to root (/) if the user is already authenticated.
   - Contains navigation Links to /login.

4. Teacher Dashboard (/teacher) [PROTECTED]
   - Access limited to authenticated users with the TEACHER role.
   - Reusable components make it easy to inspect and manage data layouts:
     * ExamList: Grid that iterates and renders individual ExamCards.
     * ExamCard: Styled panel showing exam name, total question counts, and a status tag ('published' or 'draft'). Includes button to trigger scores lookup.
     * ScoreTable: Data grid representing student grades for the active exam with loaded indicators and clear close actions.
   - Real-time success and failure alert reports using NotificationService.

5. Student Portal (/student) [PROTECTED]
   - Access limited to authenticated users with the STUDENT role.
   - Allows search and loading of exams by ID.
   - Multiple-choice question interface and submission card.

6. Services Sandbox Page (/sandbox) [PROTECTED]
   - Access limited to authenticated logged-in users.
   - Test bench for StorageService, NotificationService, LoggerService, and ConfigurationService.


PROTECTED ROUTES
================
A custom React router component, ProtectedRoute (ProtectedRoute.jsx), secures specific endpoints:
1. User Authentication Check:
   - Reads the active user token from StorageService.
   - If no session exists, the component overrides the request and redirects the user to /login.
2. User Role Authorization Check:
   - If an allowedRole attribute is provided (e.g. TEACHER or STUDENT), the component verifies if the user's role matches.
   - If the role does not match, the user is redirected to their appropriate home page (e.g., a student trying to access /teacher is rerouted to /student).


NAVIGATION MENU (NavigationMenu.jsx)
====================================
The NavigationMenu component acts as the global client-side navigation menu rendered dynamically once a user session is active.
- Features:
  * Brand Link: Points back to root (/).
  * Context-Sensitive Navigation Links:
    - Renders the "👨‍🏫 Teacher Dashboard" button ONLY if the user has the TEACHER role.
    - Renders the "🎓 Student Portal" button ONLY if the user has the STUDENT role.
    - Renders the "🛠️ Services Sandbox" link to all authenticated users.
  * Status Indicators: Displays the active user's full name and role badge clearly.
  * Logout Button: Clears local storage session via AuthService, updates state, and routes the user back to /login.


AUTH FLOW
=========
1. User opens the app
2. App initializes the HashRouter and reads active sessions from localStorage.
3. If unauthenticated, all attempts to hit protected endpoints (/teacher, /student, /sandbox) are blocked and redirected to /login.
4. User logs in or registers. The session is serialized into localStorage under the "examapp_current_user" key.
5. React state is updated, rendering the NavigationMenu.
6. The user is redirected to the home route (/), which resolves to /teacher or /student depending on their role.


TEACHER DASHBOARD DATA FLOW
===========================
1. Mount Trigger:
   - When hitting /teacher, TeacherDashboard component mounts.
   - Triggering a call to examService.getAllExams() (simulating a network fetch delay).
2. UI Card Binding:
   - On successful fetch, the array is saved to the local `exams` state and passed down to ExamList.
   - ExamList maps over the array and renders an ExamCard for each.
   - NotificationService logs a success trigger, visible under Services Sandbox logs.
3. Scores Retrieval:
   - Clicking "View Scores" on a card calls getScoresByExam(examId) with the selected id.
   - ScoreTable shows a loader spinner.
   - On response, state is updated with the student grades array, and the loader switches to a standard table display.
   - NotificationService tracks successful retrievals and prints them to sandbox logs.
4. Exception Handling:
   - If any API promise fails (e.g., mockDB network error), a catch handler triggers NotificationService.error() which renders visual toast blocks and schedules log outputs.


TEACHER EXAM CRUD MANAGEMENT FLOW
=================================
1. Create Flow:
   - Teacher clicks "+ Create New Exam" on the Teacher Dashboard.
   - The ExamForm component mounts in creation mode.
   - The teacher enters an exam title and adds/modifies questions (each with text, 4 options, and a correct answer selection).
   - Upon submitting, validation is performed: checking that the title is not empty, and all questions have text, options, and a selected correct answer.
   - Once validated, createExam(payload) from examService is called.
   - The new exam is stored in the mock database (mockDb.js) in the `exams` array with a generated auto-incrementing ID.
   - On success, the UI refreshes the exam list, displays a success toast via NotificationService, and logs the success in LoggerService.

2. Edit Flow:
   - Teacher clicks the "✏️ Edit" button on any ExamCard.
   - The ExamForm component mounts in edit mode, populated with the selected exam's current title and questions.
   - The teacher modifies the title or questions and submits.
   - After validation, updateExam(id, updates) from examService is called.
   - The mock database is updated with the modified exam object.
   - On success, the UI refreshes, notifies the user via NotificationService, and logs the action in LoggerService.

3. Delete Flow:
   - Teacher clicks the "🗑️ Delete" button on an ExamCard.
   - The DeleteExamModal confirmation dialog is displayed, showing the exam title.
   - The teacher confirms deletion.
   - deleteExam(id) from examService is called.
   - The exam is spliced and removed from the `exams` array in the mock database.
   - On success, the exam card is removed from the UI, a success notification is shown, and the action is logged in LoggerService.

4. Data Structure of Exam:
   - Each exam object has the following shape:
     {
       id: number,
       title: string,
       status: string (e.g. 'draft', 'published'),
       questions: Array<{
         id: string,
         text: string,
         options: Array<string>,
         correctAnswer: string
       }>
     }

5. Service Functions Used:
   - examService.createExam(exam)
   - examService.updateExam(id, updates)
   - examService.deleteExam(id)
   - examService.getAllExams() (to refresh the dashboard exam list)

6. Mock DB Storage:
   - The data is kept in-memory in the `exams` array exported by `api/mockDb.js`.


EXAM STATUS MANAGEMENT
======================
1. Status Rules:
   - draft: Newly created or inactive exams. Visible ONLY to teachers on their dashboard. Hidden entirely from students.
   - published: Active exams. Visible to both teachers and students. Students can search for and take published exams.
   - closed: Ended exams. Visible on the teacher dashboard. Cannot be started or submitted by students.

2. Teacher Flow:
   - Teachers can toggle/change the status of any exam card using an interactive dropdown selection (combobox) in the card's header.
   - Changing status calls updateExam(examId, { status: newStatus }) via examService.
   - It notifies the teacher of a successful state transition via NotificationService and logs the change via LoggerService.

3. Student Restriction Flow:
   - When a student searches for an exam ID in StudentPortal:
     - The portal fetches the exam via getExamById(id).
     - If the exam is not found or has status other than 'published' (i.e. 'draft' or 'closed'), access is denied and an error message is shown.
   - When submitting the answers:
     - The portal does a final fetch of the exam status.
     - If the exam was closed or drafted by the teacher while the student was taking it, submission is blocked and an error alert is displayed.
     - Successfully submitted active exams trigger a NotificationService success message and are logged in LoggerService.

4. Data Changes in Mock DB:
   - The status is stored in each exam object in the `exams` array (inside `api/mockDb.js`) as a string property named `status` with one of three values: 'draft', 'published', or 'closed'.


GENERIC SUPPORTING SERVICES
===========================
These OOP service classes are fully generic, reusable modules built to support any client-side JavaScript or React application, independent of ExamApp business logic.

1. StorageService (StorageService.js)
   - Reusability: Generic key-value wrapper for window.localStorage. Handles JSON serialization/deserialization transparently, provides optional default values, and scopes storage operations using a custom key prefix namespace.
   - Core API:
     * set(key, value): Serializes and stores key.
     * get(key, defaultValue): Deserializes key, returns defaultValue if not found.
     * remove(key): Removes key.
     * clear(): Clears all keys starting with the namespace prefix.

2. NotificationService (NotificationService.js)
   - Reusability: Decouples notification trigger logic from UI components. Any component or service can trigger a message, and UI components can register listeners to receive them instantly.
   - Core API:
     * success(message): Registers and dispatches a success alert, logging to history.
     * error(message): Registers and dispatches an error alert, logging to history.
     * warning(message): Registers and dispatches a warning alert, logging to history.
     * getHistory(): Returns full chronological array of triggered notifications.
     * clearHistory(): Resets local activity log history.
     * subscribe(listener): Registers callbacks triggered upon new alerts. Returns an unsubscribe handler.

3. LoggerService (LoggerService.js)
   - Reusability: Provides standardized audit trailing. Centralizes application log collections, useful for remote tracking or local console debugging.
   - Core API:
     * info(message): Stores an INFO level log with timestamp.
     * success(message): Stores a SUCCESS level log with timestamp.
     * error(message): Stores an ERROR level log with timestamp.
     * warning(message): Stores a WARNING level log with timestamp.
     * getLogs(): Returns the logs collection (capped at the last 10 entries).
     * clearLogs(): Resets logs.

4. ConfigurationService (ConfigurationService.js)
   - Reusability: Consolidates environment metadata, static defaults, and backend parameters. Helps swap environment variables or static constants dynamically.
   - Core API:
     * get(key, defaultValue): Retrieves static configuration value or fallback.
     * set(key, value): Sets configuration overrides dynamically.
     * getAll(): Returns cloned object of current configuration keys and values.


MOCK DB AND API
===============
The app uses an in-memory mock database (mockDb.js) containing:
- users: array of user objects with id, username, password, fullName, and role (TEACHER or STUDENT)
- exams: array of exam objects, each with id, title, status, and questions array
- studentScores: array of score records with studentName, examId, and score

Services layer:
- userService.js: findUserByCredentials, findUserByUsername, createUser (400ms simulated delay)
- examService.js: getAllExams, getExamById, createExam, updateExam, deleteExam, getAllScores, getScoresByExam (600ms simulated delay)

OOP Services:
- StorageService (class): wraps localStorage with prefix namespacing and JSON serialization
- AuthService (class): login, register, logout, getCurrentUser, isLoggedIn, getRole, isTeacher, isStudent

This layer is designed so that when a real backend is built, only the service imports need to change.

UNIT & COMPONENT TESTS
======================
All services and routing components are fully covered by automated unit tests running on Vitest under the browser-like jsdom environment.

1. StorageService Test Cases:
   - Saves and retrieves values with full serialization integrity.
   - Gracefully returns defined fallbacks/default values on non-existent keys.
   - Removes targeted keys successfully.
   - Clears prefixed keys cleanly without modifying native outside localStorage items.

2. LoggerService Test Cases:
   - Registers all levels of logs (INFO, SUCCESS, ERROR, WARNING) with automatic timestamps.
   - FIFO Buffer: Caps total in-memory size to the configured threshold (e.g. 5 or 10), shifting out oldest records as new ones arrive.
   - Clears logs cache accurately.

3. NotificationService Test Cases:
   - Dispatches success, error, warning objects with unique, automatic IDs and timestamps.
   - Forwards logs automatically to the integrated LoggerService.
   - Subscriber system: Correctly notifies all active listeners and stops dispatching once unsubscribe handles are run.

4. ConfigurationService Test Cases:
   - Returns default configurations correctly (appName, version, defaultRole, API delay).
   - Returns fallback variables if key doesn't exist.
   - Modifies and overrides existing parameters or appends new metadata properties at runtime.

5. NavigationMenu and Routing Test Cases:
   - Navigation links: Renders TEACHER links (Teacher Dashboard, Services Sandbox) and suppresses STUDENT links when a teacher logs in.
   - Navigation links: Renders STUDENT links (Student Portal, Services Sandbox) and suppresses TEACHER links when a student logs in.
   - ProtectedRoute: Blocks access to restricted paths (/teacher) and redirects to index when a user with the wrong role attempts entry.
   - ProtectedRoute: Seamlessly yields inner child components when the correct user role matches.
   - Unauthenticated Redirects: Denies access to protected components entirely if no session is active.

6. TeacherDashboard Test Cases:
   - Loading Screen: Confirms loading spinner appears while fetching list elements from mock API.
   - Exams Binding: Verifies exam card bindings (titles, question size, status) resolve on successful response.
   - Click Scores: Confirms click events trigger data calls and accurately map scores to clean tables.
   - Error handling: Confirms API exception triggers result in correct NotificationService.error calls.


DEVELOPMENT RULES
=================
- All work is done on the dev branch, never directly on main
- Feature branches are created from dev (e.g. feature/auth-login-register, feature/generic-services, feature/routing-navigation, feature/teacher-dashboard)
- Every module or feature gets its own separate commit
- Comments and notes are committed separately after each feature
- The project follows modular development: services first, then teacher features, then student features
