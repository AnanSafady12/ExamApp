EXAMAPP — FULL PROJECT FEATURE DOCUMENTATION
============================================
Last Updated: July 2026
Version: Production (Full-Stack with Docker Compose)


PROJECT GOAL
============
ExamApp is a full-stack online examination platform built for university-level course assessment management.

Teachers create and manage exams, monitor live student activity, publish results, and review grades.
Students register, browse published exams, take timed assessments, and view their graded results.

The project runs as three containerized services via Docker Compose:
  - A React + Vite frontend application (port 5173)
  - A Node.js + Express REST API backend (port 3001)
  - A PostgreSQL 15 relational database (port 5432)


USERS
=====
1. Teacher
   - Creates, edits, and deletes exams with full question management
   - Sets exam status (draft, published, closed)
   - Monitors live active students during published exams (via WebSockets)
   - Live chat with individual students or all students during an exam
   - Views all student submissions and scores per exam
   - Publishes results to release grades to students
   - Exports exam scores as CSV files

2. Student
   - Registers and logs into the platform
   - Views a filtered list of all published exams
   - Takes timed multiple-choice exams with per-question navigation
   - Submits answers and receives instant auto-graded score
   - Views published results (only after the teacher releases them)
   - Chats with the teacher during a live exam session


TECH STACK
==========
Frontend:
  - React 19 + Vite (JavaScript)
  - React Router 6 (HashRouter for SPA routing)
  - Bootstrap 5.3 (UI layout and components)
  - Vanilla CSS (custom design tokens and theme system)
  - Socket.io-client (real-time WebSocket communication)
  - Recharts (score distribution charts for teachers)
  - Vitest + jsdom (47 automated tests)

Backend:
  - Node.js + Express (REST API server)
  - Socket.io (WebSocket server for real-time events)
  - pg (node-postgres driver for direct SQL queries)
  - bcryptjs (password hashing)
  - jsonwebtoken (JWT-based stateless authentication)

Database:
  - PostgreSQL 15 (relational, persistent storage)
  - Schema managed via raw SQL (schema.sql)
  - Seeded with default user accounts and exams (seed.js)

Infrastructure:
  - Docker Compose (3-service containerized deployment)
  - Docker Bridge Network (isolated container networking)
  - Persistent named volume for PostgreSQL data (pgdata)

DATABASE SCHEMA
===============
Three PostgreSQL tables managed via raw SQL:

1. users
   - id: UUID (primary key, auto-generated)
   - username: VARCHAR(255) UNIQUE NOT NULL
   - password: VARCHAR(255) NOT NULL (bcrypt hashed)
   - role: VARCHAR(50) CHECK ('TEACHER' | 'STUDENT') NOT NULL
   - name: VARCHAR(255) NOT NULL
   - created_at: TIMESTAMP

2. exams
   - id: UUID (primary key, auto-generated)
   - title: VARCHAR(255) NOT NULL
   - time_limit: INTEGER DEFAULT 60 (in minutes)
   - passing_grade: INTEGER DEFAULT 60 (percentage threshold)
   - shuffle_questions: BOOLEAN DEFAULT FALSE
   - questions: JSONB NOT NULL (array of { id, text, options[], correctAnswer, type })
   - status: VARCHAR(50) CHECK ('draft' | 'published' | 'closed') DEFAULT 'draft'
   - results_released: BOOLEAN DEFAULT FALSE
   - created_at: TIMESTAMP

3. submissions
   - id: UUID (primary key, auto-generated)
   - exam_id: UUID FOREIGN KEY -> exams(id) ON DELETE CASCADE
   - student_id: UUID FOREIGN KEY -> users(id) ON DELETE CASCADE
   - score: INTEGER NOT NULL (percentage, 0-100)
   - answers: JSONB NOT NULL (object mapping questionId -> studentAnswer)
   - submitted_at: TIMESTAMP


REST API ENDPOINTS
==================
All endpoints below (except auth) require a valid JWT Bearer token in the Authorization header.

Authentication:
  POST   /api/users/register          Register a new user account (name, username, password, role)
  POST   /api/users/login             Log in and receive a JWT token
  GET    /api/users/by-username/:u    Check if a username is already taken (real-time availability)

Exams (all users):
  GET    /api/exams                   Get all exams (students see only 'published'; teachers see all)
  GET    /api/exams/:id               Get a single exam by ID including questions

Exams (Teacher only):
  POST   /api/exams                   Create a new exam with title, time limit, and questions
  PUT    /api/exams/:id               Update exam title, status, questions, or configuration
  DELETE /api/exams/:id               Delete an exam and all its submissions (CASCADE)
  POST   /api/exams/:id/publish-results  Release grades to students for a specific exam

Scores:
  GET    /api/scores/:examId          Get all student submission records for an exam (teacher only)
  POST   /api/scores                  Submit a new score record on exam completion (students)


AUTH FLOW
=========
1. User visits the app — React reads localStorage for an active session token.
2. If no session exists, all protected routes (/teacher, /student, /sandbox) redirect to /login.
3. User logs in via POST /api/users/login:
   - Server verifies username + bcrypt hashed password against PostgreSQL.
   - On success, the server signs and returns a JWT (payload: id, role, name).
4. The client stores the JWT and user info in localStorage via StorageService.
5. React state is updated — the NavigationMenu is rendered.
6. HomeRedirect routes the user to /teacher or /student based on their role.
7. All subsequent API calls attach the JWT in the Authorization header.
8. The server middleware (authMiddleware.js) verifies the JWT on every protected request.
9. Teacher-only endpoints additionally check req.user.role === 'TEACHER', returning 403 if not.

TEACHER DASHBOARD DATA FLOW
============================
1. Mount:
   - TeacherDashboard mounts and calls getAllExams() (HTTP GET /api/exams).
   - Results are rendered in ExamList.jsx as a styled data table.
   - useTeacherNotifications hook connects a background Socket.io client to all published exam rooms, listening for incoming student messages and tracking unread counts.

2. Exam CRUD:
   Create:
     - Teacher clicks "+ Create New Exam", ExamForm mounts in create mode.
     - Inputs: exam title, time limit (minutes), passing grade (%), shuffle toggle.
     - Questions added dynamically: each question needs text, 4 options, and a selected correct answer.
     - Client-side validation ensures no empty fields before submitting.
     - On submit: POST /api/exams — server saves to PostgreSQL and returns the new exam.

   Edit:
     - Teacher clicks "Edit" on a row, ExamForm mounts in edit mode with pre-filled data.
     - On submit: PUT /api/exams/:id — server updates the record and returns the updated exam.

   Delete:
     - Teacher clicks "Delete", DeleteExamModal confirmation overlay appears.
     - On confirm: DELETE /api/exams/:id — server removes exam and cascades all submissions.

3. Status Management:
   - Inline status dropdown per exam row (Draft / Published / Closed).
   - Changing calls PUT /api/exams/:id with { status: newStatus }.
   - Only 'published' exams are visible to students.
   - Closed exams: students cannot start them; mid-exam submissions are blocked.

4. Scores & Results:
   - Teacher clicks "View Scores" — ScoreTable mounts, calling GET /api/scores/:examId.
   - Table shows: student name, score percentage, pass/fail badge, and submission timestamp.
   - Recharts bar chart visualizes score distribution in grade ranges.
   - "Export CSV" downloads all scores as a comma-separated file.
   - "Publish Results" calls POST /api/exams/:id/publish-results — sets results_released=true in the DB, making scores visible to students.

5. Live Monitor (WebSocket):
   - Clicking "📡 Live Monitor" on a published exam opens LiveMonitorModal.
   - Modal layout: Chat Support Panel (left) | Live Student Activity Board (right).
   - Chat Panel: real-time bidirectional messages. Teacher can message "Broadcast to All" or target individual students.
   - Activity Board: live-updating list of all students currently in the exam showing:
       * Connection status: 🟢 Online (heartbeat < 10s old) or ⚪ Offline.
       * Current question number (e.g. "Question 3/10").
       * Time remaining formatted as MM:SS.
       * Visual progress bar (percentage complete).
       * ⚠️ Warning count badge (red) if student has triggered tab-switch violations.
   - Student card border turns alert red when warnings > 0.


STUDENT PORTAL DATA FLOW
=========================
1. Exam List:
   - On mount, StudentPortal calls getAllExams() (GET /api/exams).
   - Server returns only 'published' exams for STUDENT role.
   - StudentExamList renders a card grid of available exams with title, question count, and time limit.

2. Taking an Exam:
   - Clicking "Start Exam" mounts ExamTakingView with the selected exam data.
   - Questions are optionally shuffled (Fisher-Yates algorithm) based on exam configuration.
   - Features:
       * Countdown timer (timeLimit minutes converted to seconds, displayed as MM:SS).
       * Per-question navigation using previous/next buttons and direct question index selectors.
       * Answers saved in local state as student navigates.
       * Submit button is disabled until every question has been answered.
       * Auto-submit triggers when timer reaches zero.
       * ChatWidget mounted for real-time chat with the teacher during the exam.
       * Anti-cheating: Browser visibility and window focus listeners raise a warning modal if the student switches tabs or windows. Warning count increments and is reported to the teacher's live activity board in real time via WebSocket.
       * Grace period: violations within the first 1.5 seconds of mounting are ignored to prevent false positives on page load.

3. Submission:
   - On submit, the portal re-fetches the exam via GET /api/exams/:id to validate it is still published.
   - If the exam was closed mid-session, submission is blocked with an error.
   - Score calculated: (correct answers / total questions) * 100.
   - POST /api/scores — score record saved to PostgreSQL with answers JSONB and percentage.
   - After submission, QuestionCards display correct/incorrect highlights for review.

4. Viewing Results:
   - Once results are released by the teacher, students can view their score from the portal.


REAL-TIME WEBSOCKET SYSTEM (Socket.io)
=======================================
The WebSocket layer enables bi-directional real-time communication between students, teachers, and the server during live exams.

Server: socketHandler.js (initialized on the same HTTP server as Express)

Socket Rooms:
  - exam_${examId}_all          — all participants (students + teacher) in an exam
  - exam_${examId}_teachers     — teachers monitoring an exam
  - exam_${examId}_user_${userId} — private room per student

Server Events Handled:
  join_exam_chat ({ examId, user }):
    - Assigns the socket to the correct rooms based on role.
    - Sends the filtered chat history to the newly connected user.

  send_message ({ examId, message, user, target }):
    - target = 'all'       -> broadcasts to all participants
    - target = 'teacher'   -> sends to teacher room + sender's private room
    - target = userId      -> sends to specific student's room + teacher room
    - Stores message in in-memory chatHistory Map keyed by examId.

  student_progress ({ examId, studentId, studentName, currentQuestion, totalQuestions, timeLeft, isOnline, warnings }):
    - Receives live metrics from each active student.
    - Broadcasts receive_student_progress to the exam's teacher room.

  disconnect:
    - Logs client disconnection.

Client Hooks:
  useChat.js:
    - Manages a Socket.io connection scoped to a specific exam.
    - Exposes: messages, isConnected, sendMessage(), sendProgress(), studentProgress state.
    - Used by both ChatWidget (students) and LiveMonitorModal (teachers).

  useTeacherNotifications.js:
    - Background socket connection maintained by TeacherDashboard.
    - Listens across all published exam rooms simultaneously.
    - Fires NotificationService.info() toast banners when a student message arrives in a non-monitored exam.
    - Tracks per-exam unread message badge counts.


AUTH & SECURITY
===============
Server-Side:
  - Passwords are hashed using bcryptjs (10 rounds) before storage in PostgreSQL.
  - Login verifies the submitted password against the stored hash using bcrypt.compare().
  - JWT tokens are signed with jsonwebtoken using a secret key (JWT_SECRET from .env).
  - Every protected API route passes through authenticateToken middleware (authMiddleware.js):
      * Extracts Bearer token from Authorization header.
      * Verifies and decodes the JWT — returns 401 if missing, 403 if invalid/expired.
      * Injects decoded user payload into req.user for downstream controllers.
  - Teacher-only routes apply an additional inline role check (req.user.role === 'TEACHER'), returning 403 if a student attempts access.

Client-Side:
  - AuthService.js (OOP class) wraps all auth logic.
  - Session is persisted in localStorage (via StorageService) under a namespaced key.
  - ProtectedRoute.jsx intercepts React Router navigation:
      * If no session: redirect to /login.
      * If wrong role: redirect to the user's correct home route.
  - All API calls in examService.js and userService.js attach the stored JWT in the Authorization header.


ANTI-CHEATING SYSTEM
====================
Implemented in ExamTakingView.jsx using native browser APIs:

Detection:
  - document.visibilitychange: triggers when the browser tab is hidden (student switches tabs).
  - window.blur: triggers when the browser window loses focus (student alt-tabs to another app or opens DevTools).

Grace Period:
  - A mountTimeRef records the timestamp when ExamTakingView mounts.
  - Any violation event triggered within 1,500ms of mount is silently ignored to prevent false positives caused by the initial page load focus sequence.

Student Experience:
  - On first and every subsequent violation, a full-screen warning modal overlay blocks interaction.
  - The modal displays the current warning count and forces the student to actively acknowledge ("I Understand") before resuming the exam.

Teacher Experience:
  - Each violation increments the local warningCount state, which is forwarded via the sendProgress WebSocket emit.
  - Teachers see a live ⚠️ {count} warning badge on the student's activity card in the LiveMonitorModal.
  - The card border turns alert red (#dc3545) for any student with warnings > 0.


GENERIC SUPPORTING SERVICES
============================
Four OOP service classes written in plain JavaScript with zero dependency on ExamApp logic.
They are fully reusable and pluggable in any future client-side project.

1. StorageService (StorageService.js)
   - Wraps window.localStorage with prefix namespacing and transparent JSON serialization.
   - Core API: set(key, value), get(key, defaultValue), remove(key), clear()

2. NotificationService (NotificationService.js)
   - Decouples notification triggers from UI components.
   - Any module can fire an alert; registered listeners receive it.
   - Core API: success(msg), error(msg), warning(msg), info(msg), getHistory(), clearHistory(), subscribe(listener)

3. LoggerService (LoggerService.js)
   - Maintains a FIFO in-memory log buffer (capped at 10 entries).
   - Core API: info(msg), success(msg), error(msg), warning(msg), getLogs(), clearLogs()

4. ConfigurationService (ConfigurationService.js)
   - Key-value runtime configuration store for environment-specific constants.
   - Core API: get(key, defaultValue), set(key, value), getAll()


EXAM STATUS LIFECYCLE
=====================
Three states determine exam visibility and student access:

  draft     -> Created or inactive. Visible only to the teacher. Hidden from students.
  published -> Active and visible to students. Students can start and submit the exam.
  closed    -> Visible on the teacher dashboard. Students cannot start or submit it.
              If a student is mid-exam when it is closed, their submission will be blocked with a clear error message.

State transitions:
  Teacher changes the inline status dropdown -> PUT /api/exams/:id { status: newStatus }
  The server updates PostgreSQL and returns the updated exam.
  All subsequent student fetches reflect the new status.


EXAM SUBMISSION & SCORE LIFECYCLE
===================================
1. Student clicks "Submit Assessment".
2. ExamTakingView re-fetches the exam to confirm it is still 'published'.
3. Score is calculated: (number of correct answers / total questions) * 100.
4. POST /api/scores sends: { exam_id, student_id, score, answers (JSONB) } to the server.
5. ScoreService.js writes the record to the submissions table in PostgreSQL.
6. The student sees their score and correct/incorrect answer highlights.
7. Teacher opens ScoreTable, calls GET /api/scores/:examId — all records returned.
8. Teacher clicks "Publish Results" — POST /api/exams/:id/publish-results sets results_released=true.
9. Students can now see their results in their portal.

DEVELOPER SUMMARY
=================
Architecture decisions and technical rationale:

- Hybrid JSONB + Relational Schema:
  Questions and student answers are stored as JSONB in PostgreSQL. This avoids creating a separate normalized questions table while retaining the power of relational DB joins for users and submissions. This is the correct approach for a schema where question structure may vary per exam type.

- JWT Stateless Authentication:
  Using JWTs instead of server-side sessions means the backend is fully stateless and horizontally scalable. Each request is self-contained and independently verifiable.

- Socket.io Room Architecture:
  Three room types (all, teachers, per-user private) enable fine-grained message routing without broadcasting private messages to unintended recipients. This is the standard pattern for multi-tenant real-time chat.

- Anti-Cheating Grace Period:
  The 1,500ms mount-time filter was necessary because all browsers fire a blur event as the browser routes to a new page, which would have caused every student to immediately accumulate a false warning on exam entry.

- Debounced Username Availability:
  The real-time username check is debounced at 400ms to prevent hammering the API on every keystroke. The UX feel is kept instant while the network load is kept minimal.

- Generic OOP Services:
  Services (Storage, Logger, Notification, Configuration) are deliberately domain-agnostic. Zero ExamApp references exist in their implementations. This was a conscious design choice to demonstrate clean separation of concerns and portability.

- Modular Component Architecture:
  Breaking TeacherDashboard and StudentPortal into smaller, single-responsibility components (ExamList, ExamForm, ScoreTable, ExamTakingView, QuestionCard, ChatWidget, etc.) makes each component independently testable, and the Vitest suite is kept clean and focused.
